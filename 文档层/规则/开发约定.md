# 轻量代码开发约定

## 模块边界与变更

模块拆分、契约边界、AI 步骤与质检激活点见 doc://demo/module-boundary；模块与入口、外部代码的存放见 doc://demo/module-layout。

模块主记录先写职责、输入输出、错误行为、读写影响、依赖和完成依据。代码与测试放代码层，完整说明留在文档层。必要的局部注释说明非显然约束，不复制主记录。

调用方使用公开接口；实现可以独立替换。变更内部实现须保持公开行为。变更公开约定时先查 depends_on 和相关记录，同步实际调用方与验证。不要改其他模块的私有文件来“修好”自己的接口。

## 输入、错误与状态

文件、配置、工具 JSON 和持久数据等实际入口校验必填、类型及关键业务条件。受同一程序静态类型保证的内部值不机械重复校验。默认值明确归属，部署变化项进配置，不散落为隐藏常量。

失败、超时、取消、部分完成和成功分别表达，错误说明对象、原因和可继续的动作。实际结果不能被一次 success 标志替代。只有写入成功后才更新完成状态；涉及多步写入时按实际影响安排临时文件替换或恢复办法。

不硬编码本机绝对路径。使用成熟库能减少维护量时直接复用，不包装成另一套通用框架。密钥不写进代码、文档或日志。

## 并行开发与检查

每次给 Agent 提供模块 URI、接口、依赖、允许修改的位置和完成标准。不同 Agent 不同时写同一文件；共享接口变更先完成，再启动依赖该变更的任务。这是任务安排规则，不要求额外开发调度平台。

对实际行为运行必要检查，重点是外部输入、错误行为、持久数据和模块组合。替身可用于独立开发；交付前通过真实入口检查组合。无证据不称验证通过，不为了全覆盖率机械扩写测试。

涉及子进程、临时目录或后台任务时，明确谁创建、谁清理及何时真正完成；没有使用这些机制就不预建其设施。修复检查失败的原因，不改测试数据或降低标准掩盖失败。

完成后按 doc://demo/workflow 同步代码、现行文档和关系。工具只能发现结构及指纹变化，语义与业务结果仍由执行 Agent 核对。
