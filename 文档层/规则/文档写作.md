# 文档写作与维护规则

## 归属

项目主记录回答整体目标和当前入口；模块主记录回答职责、输入输出、开发管理和关联资料。专题文档解释超过主记录篇幅的细节。决策记录解释为什么这样选择，活动记录保存过程和接续。机器字段以代码中的类型或 schema 为定义来源，文档写语义及条件，索引从来源生成。

每个事实只有一个维护位置，其余通过 URI 引用。主记录可以保留导航性摘要，不另写第二套完整规则。新增文档先确认已有文件能否承担。

## 写法

中文为主，UTF-8；标题和段落直述对象、动作、条件及后果。必要的英文标识保留。教程按操作顺序，参考说明按问题或对象组织，实质不同的长内容才拆分。

现行说明描述当前行为；计划用 draft、planned 或 proposed 明确标记。历史过程放演进记录。保留失败条件、时序、读写影响、例外和限制，不写实现推演、测试逐行走读或自证正确的话。

一段一条完整含义，段落用编辑器软换行。入口建议一屏到两屏，模块主记录建议约 600—1200 中文字；这是导航预算，超出先把专题移到其归属处，不为凑字数删除必要约定，也不通过抬高预算放行。

## 元信息与引用

正式 Markdown 必须具有 name、uri、type、created、updated、status、related、tags；非项目对象增加 project。日期为 YYYY-MM-DD，更新内容同步 updated。document 增加 kind，专门关系写入 links；完整定义见 doc://demo/ontology。

文档及模块身份使用 project、module、doc、decision、activity、code URI。正式引用在 related 或 links 登记，重要关系不能只出现在正文。CLI 检查正文 URI 是否可识别，不自动推断正文语义。绝对目录仅存在本机绑定配置，不写进可复用说明。

文件名：现行与稳定文档用稳定描述名，不加 v1/v2/final 等版本后缀；时间序列记录（决策、作业）用 YYYY-MM-DD-主题；模板用 名称.模板.md。类型与关系命名见 doc://demo/ontology。

模板目录中的文件是待实例化文本，不参加资产索引；复制到正式位置、填写标记、分配唯一 URI 后才成为资产。

## 自查清单（文档坏味道）

写作后按下列清单自查，命中即修：

- **重复规则**：同一规则出现在多处。保留一个归属，其余改为引用。
- **历史外泄**：现行文档里写“过去是……现在是……”。历史放演进记录，现行只写当前。
- **状态标注**：正文或图里写“已实现！”“未来：……”。状态会腐坏，交给代码与清单。
- **手工复述**：手工复制可由源或命令生成的清单、字段、目录。改为引用来源。
- **推理转录**：逐步实现叙述、显然分支的证明、测试逐行走读、被否方案的过程。只留结论与理由。
- **段落墙**：一段塞进多条规则和括号补充。拆分或下沉到其归属。
- **强调通胀**：到处加粗、大写、“关键”。强调只留给改变行为的那一句。
- **spec-speak**：在已实现文档里写“应当……”、计划、验收清单。已实现只写实际决定与后果。

## 更新与留痕

当前文件持续更新，不按每次讨论累积 v1-final、v2-final 等多个权威版本。需要改变一个重要决定时新建决策并标明替代关系，保留真实备选与代价。普通修正更新现有文件和活动结果即可。

归档边界与决策状态由 doc://demo/evolution-rules 持有。任何文件移动后重新索引并检查入站引用；URI 不随路径变化。
