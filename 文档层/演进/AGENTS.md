# 演进记录与生命周期规则

活动记录回答一次任务发生了什么、完成什么、如何接续；重要决策回答为什么这样选择、真实备选及代价。当前模块行为由主记录与现行专题持有。跨模块记录只写一份，通过 affects 关联各对象。

## 决策状态

proposed 是未完整交付的提案，必须包含问题、真实备选、提案与验收。implemented 描述已落地决定和后果，必须包含问题、真实备选、决定与后果。rejected 保留原提案及明确拒绝原因；只有仍能防止重走错误路线的记录才保留为日常上下文。

与 DSH 一致，归档已实施决策保持 status: implemented，增加 archived_at 日期。默认 context 不读取归档正文，--history 才加入；不得把归档重新当成现行规则。归档按历史快照保留，纠正另写说明，不为了新格式改写旧记录。本版不实现 DSH 的哈希封存门禁。

## 替代与引用

新决策先查旧决策。完整替代用 supersedes；仅部分替代时用 related 相联，在双方明确仍有效的范围，不能将旧记录改写成相反决定。proposed 过时应明确 rejected，不能通过归档逃避结论。删除历史不属于工具自动动作。

决策存放位置不编码状态，避免再维护一套目录状态；CLI 从 YAML 分类。因此保留 DSH 的三态与归档含义，裁掉四套生命周期目录和分类子目录。

## 作业记录

一次有意义的活动一份记录，包含目标、已完成、验证与问题、下一步；重要状态更新时续写，不为每个命令新增文件。阶段结果保留发生日期和适用范围，不把历史计数当当前计数。

模板见文档层的模板目录。文件名推荐 YYYY-MM-DD-中文主题.md，现行专题文件名稳定，不随每轮讨论加版本号。

## 反复问题沉淀

同一类问题反复出现、且造成实际损失（不只是笔误）时，除了写活动记录，还应把它沉淀为规则或检查：明确触发条件、应有动作和失败处理，写入相应规则文件；能让机器检查的，再固化为 CLI 检查项。一次性笔误不升级为规则。目的：让同类问题在下一轮显式暴露，而不是重复踩坑。
