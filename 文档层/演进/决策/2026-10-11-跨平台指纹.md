# 指纹跨平台归一化

## 问题

核对指纹对文件原始字节做哈希。同一个文档在 Windows 检出（CRLF）与 Linux 检出（LF）下字节不同，指纹随之不同：在 Windows 登记的核对指纹，到 Linux 上 check --strict 会报“发生变化，需重新核对”，即使内容一字未改。这不是内容变化，而是换行格式差异被当成了变化。工具定位是可复制、跨平台的项目骨架，这个差异会让新环境开箱即失败。

发现于 2026-10-11：外部工具在 Windows 交付的 L3 规则层，在 Linux 复现时 check --strict 失败，逐对象比对确认为 CRLF/LF 差异，不是内容改动。

## 真实备选

- **仓库加 .gitattributes 固定 LF（text=auto eol=lf）。** 让各处检出都用 LF，工作区字节一致。但依赖每个使用者的 git 配置遵守，对已经存在的 CRLF 检出无效，二进制文件的处理还要额外小心。未采用为唯一手段。
- **在指纹计算内归一行尾与 BOM。** 让指纹只看文本内容，不看平台换行；二进制文件原样哈希，不影响。工具可复制、跨平台稳定。采用。
- **维持现状，靠人工换环境后重新 checkpoint。** 每次换环境都要重登指纹，把格式差异当内容变化处理，违背“指纹反映内容变化”的语义。未采用。

## 决定与后果

catalog.py 增加 canonical_bytes()，在 digest() 内先对可解码为 UTF-8 的内容归一 BOM 与行尾（CRLF/CR → LF）再哈希，二进制内容原样哈希。test_cli.py 增加用例，模拟 CRLF 检出后指纹不变、check --strict 仍通过。

后果：指纹从此只随文本内容变化，不随换行格式变化，跨平台可复现；核对指纹按新算法重新登记一次（已在最终内容上重跑 checkpoint）。仍未覆盖 BOM 之外的其他编码差异，也不做语义一致判断——指纹只证明字节级内容稳定。
